**belay v0.1.0-alpha.11 is a pre-alpha.** It records what changed in a directory and explains it. It
changes nothing, undoes nothing, and contains nothing. Use it to look, not to protect.

## What changed since v0.1.0-alpha.10

**`belay watch` and the Claude Code plugin: a file changed and put back says so.**

- A step that returns a file to the content it had when the session started, after a step that changed it, names it: `belay: 🔴 tests/test_app.py put back (as before step 2)`. It is an item of its own, never part of a count. It is flagged when the file is a test file or on the watch's list, and noted otherwise.
- The receipt opens with a `put back` section: `tests/test_app.py: changed at step 2, as at the start again at step 3`. The plugin's Stop line counts it: `4 changed this turn, 1 put back, in 4 tool calls`.
- The steps of a session are numbered, and the receipt's headings carry the number: `session S  step N  call C`. A step is a call that changed something.
- What it proves: the file's content at the later step is byte for byte its content at the session's start, and a step between them differed. It says nothing of why. A restore that differs by a byte, a final newline among them, is a change, not a put back. `git diff` shows neither.

**A test file or a listed path touched within one step says so.**

- A change and a restore inside one tool call leave the same content at both ends of the step. For a test file, or a path the watch's list flags, belay now names it when the file's ctime (or its inode) moved and its content, mode and owner did not: `belay: 🔴 tests/test_app.py touched (content as before)`. The Stop line counts it: `, 1 touched,`.
- It is built on ctime, which a program cannot set back without root, and not on mtime, which it can.
- What it proves: the file was written, replaced, or had its metadata changed and restored during the step, and its content at the end is as at the start. It does not say what the content was in between. `touch`, a save with no change, a checkout away and back, and `chmod` and back all raise it. For every other file nothing changes: such a step still says `metadata changed`.

**`belay verify`: `tests_weakened` on a test file emptied or deleted.**

- A test file that had content and is now deleted, or holds nothing but whitespace and comments, raises `tests_weakened` with a new field `gone`: `test.py: emptied (was 41 lines)`, `tests/test_api.py: deleted`.
- A Python file named exactly `test.py` or `tests.py` is a test file. Before, only `test_*.py`, `*_test.py` and files below a tests directory were.
- Not looked for, because it needs judgement: a runner that no longer fails, a comparison rewritten, a test that no longer runs the code.
- **policy.v1's output gains an optional key.** A `tests_weakened` record may carry `gone`. A reader that rejects unknown keys needs this release.

**Unchanged:** the manifest (version 5), diff.v1, the protect spec (version 2) and the baseline bundle. The watch's own state gains a table of sessions.

**Known limits of `belay watch` and the plugin** are as [v0.1.0-alpha.8's notes](https://github.com/Allexsen/belay/blob/v0.1.0-alpha.11/docs/releases/v0.1.0-alpha.8.md) list them, the macOS one aside. The plugin records a project directory; it does not record the home directory, and says so.

## What it still can't see

A copy of the tests edited and run somewhere else leaves the test files untouched, and belay says nothing about them. A file restored within the same timestamp tick as its last change keeps its ctime, and nothing is said. Only test files and listed paths are named as touched.

A protect spec sees files, not intent: a hack that lives in code it does not protect passes, and it reports that a protected file changed, not why.

A file over 64 MiB is recorded without a hash. What a program did on the network or in memory is not recorded: belay reads files.

The limits on a concurrent writer are as v0.1.0-alpha.3's notes state them, in full:
- **Where it can't ask:** on macOS, on filesystems without leases, and for files belay's user does not own without `CAP_LEASE`, belay can't ask. On overlayfs, a shared mapping whose descriptor was closed is invisible. A torn hash there still diffs as an ordinary change; each manifest says only how many files were hashed this way, as `unguarded`.
- **A fast writer:** one that opens, writes and closes entirely between the two checks, within one timestamp tick, is seen by nothing.
- **A writer on another machine:** on a filesystem that grants leases locally, it may go unseen. This is unverified.

As in earlier releases: no undo and no sandbox -- belay records and reports and is not a security boundary.

## Files

| file | platform |
|---|---|
| `belay-v0.1.0-alpha.11-linux-x86_64` | Linux, x86_64; statically linked |
| `belay-v0.1.0-alpha.11-linux-arm64` | Linux, arm64; statically linked |
| `belay-v0.1.0-alpha.11-macos-arm64` | macOS 15, Apple silicon; links only the system library; not notarized |
| `SHA256SUMS` | the sha256 of each binary |
| pybelay wheels, `WHEELS-SHA256SUMS` | the Python bindings, version 0.1.0a11, with each wheel's sha256 |

Each binary was built from the tagged commit by the release workflow, and run end to end before it
was attached. To verify one:

```sh
sha256sum -c --ignore-missing SHA256SUMS
gh attestation verify belay-v0.1.0-alpha.11-linux-x86_64 --repo Allexsen/belay
```

On macOS the binary is not notarized: remove the quarantine attribute
(`xattr -d com.apple.quarantine belay-v0.1.0-alpha.11-macos-arm64`) or build from source.

## Status

Pre-alpha: interfaces, output and formats may change without notice. No stable API. The most useful contribution is real-world use: if belay missed a change, invented one, or buried the real one in noise, [open a mismatch issue](https://github.com/Allexsen/belay/issues/new?template=mismatch.yml). Security reports: [SECURITY.md](https://github.com/Allexsen/belay/blob/v0.1.0-alpha.9/SECURITY.md). Apache-2.0.
