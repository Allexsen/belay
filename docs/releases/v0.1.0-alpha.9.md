**belay v0.1.0-alpha.9 is a pre-alpha.** It records what changed in a directory and explains it. It
changes nothing, undoes nothing, and contains nothing. Use it to look, not to protect.

## What changed since v0.1.0-alpha.8

**`belay verify --docker`: a protected file that was written and put back.**

- A new signal, `protected_path_touched`. In a container, writing to a file of the image copies it into the container's own layer, and the copy stays there when the bytes are put back. `verify` now names such a file when it is under a `no_write` rule and nothing else about it changed. It is a signal: it never changes the verdict or the exit code.
- It is raised only when both captures were read from a container's layers (`--docker`). Elsewhere the policy's header lists it under `not_emitted`, with the reason.
- **It is silent for a file that was not in the image.** A file made after the container started is already in the container's layer, so changing it in place and restoring it leaves no trace. In an Inspect eval that covers a sample's `files=` and anything a setup step writes.
- **Honest work raises it too.** In 53 measured runs of ordinary repository work in real Docker it fired in 14: a checkout of an older commit and back, a no-op `chmod -R` or `chown -R`, discarded edits, a save with no change. Never for status, stash, commit, merge, rebase, pytest or npm.
- **policy.v1's output gains a key.** The trailer has `protected_path_touched`, and the header's `not_emitted` has an entry for it when the captures were not read from layers. A reader that rejects unknown keys, pybelay 0.1.0a8 among them, rejects this binary's policy: use the wheel of this release with this binary.

**pybelay's Inspect integration: belay outside the sandbox.**

- `belay_record(spec, where="host")`, and the `belay_verify()` that follows it, run belay on the machine the eval runs on and read the sample's Docker container from there, paused for each reading. Nothing of belay's enters the sandbox. The default is unchanged: belay runs inside the sandbox.
- **It needs root for belay, and that is a real cost.** The eval runs as root, or its user may run `timeout` through `sudo -n` without a password, which is passwordless root for that account. It also needs Linux, a Docker daemon on the same machine (not Docker Desktop), a `/tmp` that allows execution, and GNU coreutils. [python/README.md](https://github.com/Allexsen/belay/blob/v0.1.0-alpha.9/python/README.md) lists what it does on the host and what it can leave there.
- Only the wheel's own binary runs on the host: `binary=` with `where="host"` is refused.
- The container is set running again whatever became of the reading: an answer, a refusal, a timeout, a cancelled sample. If it cannot be, the error says so together with belay's answer.
- Asked for and unable to run, it fails the sample and says why. It never runs belay in the sandbox instead.
- **Not established by a run:** that the eval's user cannot signal a process sudo started, and Docker's wording for a container that is not paused, are both from those tools' sources. The eval-as-root path has run only with the user id mocked. No eval here changed and restored a file of an image, so `protected_path_touched` appearing in a score is from reading the code.

**pybelay's Inspect integration: two changes to the default mode.**

- `belay_verify` judges against the record `belay_record` kept in the process, not against the copy in the sample's store. The copy is for the log, and changing it changes nothing. Before, whatever could write the store chose what `belay_verify` ran and read.
- **Fixed:** when putting the binary into the sandbox did not finish, by a refusal or a cancelled sample, the binary stayed in the sandbox. It is taken out.

**`belay watch`: a longer built-in list.**

- 94 rows, from 66. The 28 new ones are names that Anthropic's claude-code-action treats as configuration a pull request controls, and names Claude Code 2.1.322 itself will not edit without asking. They are included by name; the pin says for each what was run to check it, if anything. 50 of the 94 rows carry a "not verified" mark, in whole or in part.
- Applied to the recorded steps the list was measured on, the new rows change no step's result.
- `.claude/.cc-writes` is no longer flagged: Claude Code writes that directory itself. Anything written inside it is still counted and listed.

**The Claude Code plugin**

- The README gives the full-URL form of the install, for a network that blocks SSH.
- macOS: the plugin was run by hand on Apple silicon (install from GitHub, the per-call lines, the red circle, `/belay:receipt`). Intel Macs have no binary.

**Unchanged:** the manifest (version 4), diff.v1, the protect spec (version 2) and the baseline bundle. `belay watch`'s lines and its hook are as before.

**Known limits of `belay watch` and the plugin** are as [v0.1.0-alpha.8's notes](https://github.com/Allexsen/belay/blob/v0.1.0-alpha.9/docs/releases/v0.1.0-alpha.8.md) list them, the macOS one aside.

## What it still can't see

A protect spec sees files, not intent: a hack that lives in code it does not protect passes, and it reports that a protected file changed, not why.

The limits on a concurrent writer are as v0.1.0-alpha.3's notes state them, in full:
- **Where it can't ask:** on macOS, on filesystems without leases, and for files belay's user does not own without `CAP_LEASE`, belay can't ask. On overlayfs, a shared mapping whose descriptor was closed is invisible. A torn hash there still diffs as an ordinary change; each manifest says only how many files were hashed this way, as `unguarded`.
- **A fast writer:** one that opens, writes and closes entirely between the two checks, within one timestamp tick, is seen by nothing.
- **A writer on another machine:** on a filesystem that grants leases locally, it may go unseen. This is unverified.

As in earlier releases: no undo and no sandbox -- belay records and reports and is not a security boundary.

## Files

| file | platform |
|---|---|
| `belay-v0.1.0-alpha.9-linux-x86_64` | Linux, x86_64; statically linked |
| `belay-v0.1.0-alpha.9-linux-arm64` | Linux, arm64; statically linked |
| `belay-v0.1.0-alpha.9-macos-arm64` | macOS 15, Apple silicon; links only the system library; not notarized |
| `SHA256SUMS` | the sha256 of each binary |
| pybelay wheels, `WHEELS-SHA256SUMS` | the Python bindings, version 0.1.0a9, with each wheel's sha256 |

Each binary was built from the tagged commit by the release workflow, and run end to end before it
was attached. To verify one:

```sh
sha256sum -c --ignore-missing SHA256SUMS
gh attestation verify belay-v0.1.0-alpha.9-linux-x86_64 --repo Allexsen/belay
```

On macOS the binary is not notarized: remove the quarantine attribute
(`xattr -d com.apple.quarantine belay-v0.1.0-alpha.9-macos-arm64`) or build from source.

## Status

Pre-alpha: interfaces, output and formats may change without notice. No stable API. The most useful contribution is real-world use: if belay missed a change, invented one, or buried the real one in noise, [open a mismatch issue](https://github.com/Allexsen/belay/issues/new?template=mismatch.yml). Security reports: [SECURITY.md](https://github.com/Allexsen/belay/blob/v0.1.0-alpha.9/SECURITY.md). Apache-2.0.
