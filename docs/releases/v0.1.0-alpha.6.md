**belay v0.1.0-alpha.6 is a pre-alpha.** It records what changed in a directory and explains it. It
changes nothing, undoes nothing, and contains nothing. Use it to look, not to protect.

## What changed since v0.1.0-alpha.5

**belay's state no longer grows without bound.** One week of dogfood hooks should stay under 1 GB.

- Checkpoints are stored as deltas against their predecessor, with a full copy every 256. Every rebuild is checked byte for byte.
- `belay prune` removes old checkpoints by age and count, the stored copies nothing refers to, and what a killed capture left behind. `--dry-run` says what would go.
- `belay mark --keep` marks a checkpoint that is never pruned.
- `belay manifest` prints any checkpoint's manifest.
- **`checkpoint.v2` replaces v1:** `manifest` is null for a delta, and `stored` and `kept` are new. Use `belay manifest` rather than reading the path.
- The dogfood hooks prune once a day, keeping 7 days.
- Receipts explain a branch switch in one line instead of listing edits and removals.
- A call gets one number in a receipt, however many sections name it.
- Every pybelay wheel carries both Linux binaries, so a Linux wheel serves a container of either architecture.
- The Inspect integration removes each sample's bundle once it is scored.

A state directory from an earlier release is read as it is: nothing is migrated, and new checkpoints become deltas. An earlier binary can't read a state with deltas.

**Limits:** a pruned checkpoint is gone, and a command naming it is refused. A bare manifest read of a delta takes up to about 8 times as long as a whole file, though `diff` and `log` stay under 1.5 times.

## What it still can't see

A protect spec sees files, not intent: a hack that lives in code it does not protect passes, and it reports that a protected file changed, not why.

The limits on a concurrent writer are as v0.1.0-alpha.3's notes state them, in full:
- **Where it can't ask:** on macOS, on filesystems without leases, and for files belay's user does not own without `CAP_LEASE`, belay can't ask. On overlayfs, a shared mapping whose descriptor was closed is invisible. A torn hash there still diffs as an ordinary change; each manifest says only how many files were hashed this way, as `unguarded`.
- **A fast writer:** one that opens, writes and closes entirely between the two checks, within one timestamp tick, is seen by nothing.
- **A writer on another machine:** on a filesystem that grants leases locally, it may go unseen. This is unverified.

As in earlier releases: no undo and no sandbox -- belay records and reports and is not a security boundary.

## Files

| file | platform |
|---|---|
| `belay-v0.1.0-alpha.6-linux-x86_64` | Linux, x86_64; statically linked |
| `belay-v0.1.0-alpha.6-linux-arm64` | Linux, arm64; statically linked |
| `belay-v0.1.0-alpha.6-macos-arm64` | macOS 15, Apple silicon; links only the system library; not notarized |
| `SHA256SUMS` | the sha256 of each binary |
| pybelay wheels, `WHEELS-SHA256SUMS` | the Python bindings, version 0.1.0a6, with each wheel's sha256 |

Each binary was built from the tagged commit by the release workflow, and run end to end before it
was attached. To verify one:

```sh
sha256sum -c --ignore-missing SHA256SUMS
gh attestation verify belay-v0.1.0-alpha.6-linux-x86_64 --repo Allexsen/belay
```

On macOS the binary is not notarized: remove the quarantine attribute
(`xattr -d com.apple.quarantine belay-v0.1.0-alpha.6-macos-arm64`) or build from source.

## Status

Pre-alpha: interfaces, output and formats may change without notice. No stable API. The most useful contribution is real-world use: if belay missed a change, invented one, or buried the real one in noise, [open a mismatch issue](https://github.com/Allexsen/belay/issues/new?template=mismatch.yml). Security reports: [SECURITY.md](https://github.com/Allexsen/belay/blob/v0.1.0-alpha.6/SECURITY.md). Apache-2.0.
