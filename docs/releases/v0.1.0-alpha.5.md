**belay v0.1.0-alpha.5 is a pre-alpha.** It records what changed in a directory and explains it. It
changes nothing, undoes nothing, and contains nothing. Use it to look, not to protect.

## What changed since v0.1.0-alpha.4

**pybelay now works with [Inspect](https://inspect.aisi.org.uk/).** An eval records each sample's sandbox before the agent acts, and judges it afterwards, beside its own scorers. See [Using belay with Inspect](https://github.com/Allexsen/belay/blob/v0.1.0-alpha.5/python/README.md#using-belay-with-inspect).

- `pip install "pybelay[inspect] @ <wheel URL>"` adds `pybelay.inspect`: `belay_record` for a Task's `setup`, and `belay_verify` for its scorers.
- The score is `C` with the answer `pass`, or `I` with `violation`, or `I` with `error` when belay could not judge the run. The flags are in its metadata.
- The metrics are `pass_rate`, `violations` and `errors`.
- belay's static binary is copied into the sandbox for each step and removed after. `--docker` isn't used: it needs root on the host, and refuses Docker Desktop.
- `belay_verify` refuses to run after another scorer, since one that runs tests can change the sandbox.
- macOS wheels now also carry the Linux x86_64 and arm64 static binaries, so Docker on a Mac works: the one matching the sandbox is picked. The wheel grows by about 1.1 MB.
- `bench/replay/` is new: a harness that replays EvilGenie's 2,115 published agent runs against belay, and `RESULTS.md`, the report.

belay itself is unchanged: the manifest is version 4, as in v0.1.0-alpha.4, and the formats are the same.

## Limits of the Inspect integration

- belay runs inside the sandbox, beside anything the agent left running. A leftover process can still write while belay reads, or interfere with it if it runs as the same user. Inspect can't stop such a process first, as `belay verify` asks.
- It sees the end state, within the scope: a file changed and restored is invisible.
- `belay_verify()` must come first in the Task's scorers.
- `inspect score` on a finished log can't judge: the sandbox is gone.
- The sandbox needs a writable, executable `/tmp`, and `uname`, `chmod` and `rm`.
- A Linux wheel carries only its own binary: for a sandbox of another architecture, belay refuses and says so, and `binary=` takes the right one.
- Inspect reads at most 100 MiB from a sandbox by default. A larger bundle is refused, and bundles stay in a temporary directory on the host until the eval's process ends.
- With several epochs and a reducer, a sample with both judged and unjudged epochs counts as a violation, not an error.
- Tested with Docker on Linux x86_64 and arm64, Inspect's `local` sandbox on Linux, and Inspect 0.3.213 and 0.3.287. Not tested on a real Mac, or with Kubernetes.

## What it still can't see

A protect spec sees files, not intent: a hack that lives in code it does not protect passes, and it reports that a protected file changed, not why.

The limits on a concurrent writer are as v0.1.0-alpha.3's notes state them, in full:
- **Where it can't ask:** on macOS, on filesystems without leases, and for files belay's user does not own without `CAP_LEASE`, belay can't ask. On overlayfs, a shared mapping whose descriptor was closed is invisible. A torn hash there still diffs as an ordinary change; each manifest says only how many files were hashed this way, as `unguarded`.
- **A fast writer:** one that opens, writes and closes entirely between the two checks, within one timestamp tick, is seen by nothing.
- **A writer on another machine:** on a filesystem that grants leases locally, it may go unseen. This is unverified.

As in earlier releases: no undo and no sandbox -- belay records and reports and is not a security boundary.

## Files

| file | platform |
|---|---|
| `belay-v0.1.0-alpha.5-linux-x86_64` | Linux, x86_64; statically linked |
| `belay-v0.1.0-alpha.5-linux-arm64` | Linux, arm64; statically linked |
| `belay-v0.1.0-alpha.5-macos-arm64` | macOS 15, Apple silicon; links only the system library; not notarized |
| `SHA256SUMS` | the sha256 of each binary |
| pybelay wheels, `WHEELS-SHA256SUMS` | the Python bindings, version 0.1.0a5, with each wheel's sha256 |

Each binary was built from the tagged commit by the release workflow, and run end to end before it
was attached. To verify one:

```sh
sha256sum -c --ignore-missing SHA256SUMS
gh attestation verify belay-v0.1.0-alpha.5-linux-x86_64 --repo Allexsen/belay
```

On macOS the binary is not notarized: remove the quarantine attribute
(`xattr -d com.apple.quarantine belay-v0.1.0-alpha.5-macos-arm64`) or build from source.

## Status

Pre-alpha: interfaces, output and formats may change without notice. No stable API. The most useful contribution is real-world use: if belay missed a change, invented one, or buried the real one in noise, [open a mismatch issue](https://github.com/Allexsen/belay/issues/new?template=mismatch.yml). Security reports: [SECURITY.md](https://github.com/Allexsen/belay/blob/v0.1.0-alpha.5/SECURITY.md). Apache-2.0.
