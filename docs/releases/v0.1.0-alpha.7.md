**belay v0.1.0-alpha.7 is a pre-alpha.** It records what changed in a directory and explains it. It
changes nothing, undoes nothing, and contains nothing. Use it to look, not to protect.

## What changed since v0.1.0-alpha.6

Two fixes for things that were broken for a user of v0.1.0-alpha.6. No format changes.

**`belay verify` no longer reports a protected directory as written because files were created in it.**

- ext4 sets a directory's hashed-index flag by itself when the directory outgrows one block. belay recorded that as an inode-flag change and called it a privilege change. With a `no_write` rule covering the directory, for example `tests/**`, creating a few hundred files in it made `verify` report `protected_path_written` on the directory and exit 1. pybelay's reward helper turns that into a reward of zero.
- Now, on a directory, a change to inode flags is a privilege change only when immutable or append-only is set or cleared. The same rule holds in `privilege_changed` and in the receipt's privilege section. It is pinned in [test/expect/inode-flags.md](https://github.com/Allexsen/belay/blob/v0.1.0-alpha.7/test/expect/inode-flags.md), with the measurement behind it: 10,990,360 entry comparisons over 2,789 checkpoints showed no such change on a regular file.
- **If you judged runs with an earlier release:** a `protected_path_written` whose `path` is a directory and whose `changed` is exactly `["iflags"]` was this defect.
- `privilege_changed` no longer reports an entry whose flags could be read at one end only (`iflags 0 -> none` on a file made unreadable). A protected path in that state is still `protected_path_unverifiable`.
- The receipt now names an entry that is added or removed holding immutable or append-only. A flag change that is no privilege change is still shown, among the other changes.
- Nothing is hidden: the manifest records inode flags as before, and diff.v1 lists `iflags` in `changed` as before.

**The Inspect install line works again on a clean machine.**

- Since 9 November 2026 a fresh install of `pybelay[inspect]` could not run an eval: `agent-client-protocol` 1.0.0 removed a module that `inspect-ai` imports, and `inspect-ai` does not bound that package. The failure is `No module named 'acp.helpers'`, with or without pybelay.
- The documented line now holds that package below 1.0:

  ```
  pip install "pybelay[inspect] @ https://github.com/Allexsen/belay/releases/download/v0.1.0-alpha.7/pybelay-0.1.0a7-py3-none-manylinux_2_17_x86_64.musllinux_1_1_x86_64.whl" "agent-client-protocol<1"
  ```

  To repair an environment already installed: `pip install "agent-client-protocol<1"`. Drop the bound once an Inspect release fixes its requirement.
- pybelay's own code is unchanged; its wheels carry this release's binary.

**Unchanged:** the manifest (version 4), diff.v1, policy.v1, the protect spec (version 2) and the baseline bundle. A state directory and a bundle from v0.1.0-alpha.6 are read as they are.

**Limits of the inode-flag rule:**

- On a directory, every flag other than immutable and append-only is now silent as a privilege change, not only ext4's hashed index: no-dump, no-atime and the like, which a directory's owner can set. The change is still in the diff and the receipt.
- A manifest is judged by the locking flags of the platform that judges it. A bundle written on macOS and verified on Linux, or the reverse, would not see the other platform's immutable flag on a directory. Verify where you exported.
- A file replaced by a symlink is still reported as `iflags N -> none`, as before: a symlink has no inode flags.

## What it still can't see

A protect spec sees files, not intent: a hack that lives in code it does not protect passes, and it reports that a protected file changed, not why.

The limits on a concurrent writer are as v0.1.0-alpha.3's notes state them, in full:
- **Where it can't ask:** on macOS, on filesystems without leases, and for files belay's user does not own without `CAP_LEASE`, belay can't ask. On overlayfs, a shared mapping whose descriptor was closed is invisible. A torn hash there still diffs as an ordinary change; each manifest says only how many files were hashed this way, as `unguarded`.
- **A fast writer:** one that opens, writes and closes entirely between the two checks, within one timestamp tick, is seen by nothing.
- **A writer on another machine:** on a filesystem that grants leases locally, it may go unseen. This is unverified.

As in earlier releases: no undo and no sandbox -- belay records and reports and is not a security boundary.

Each binary was built from the tagged commit by the release workflow, and run end to end before it
was attached. To verify one:

```sh
sha256sum -c --ignore-missing SHA256SUMS
gh attestation verify belay-v0.1.0-alpha.7-linux-x86_64 --repo Allexsen/belay
```

On macOS the binary is not notarized: remove the quarantine attribute
(`xattr -d com.apple.quarantine belay-v0.1.0-alpha.7-macos-arm64`) or build from source.

## Status

Pre-alpha: interfaces, output and formats may change without notice. No stable API. The most useful contribution is real-world use: if belay missed a change, invented one, or buried the real one in noise, [open a mismatch issue](https://github.com/Allexsen/belay/issues/new?template=mismatch.yml). Security reports: [SECURITY.md](https://github.com/Allexsen/belay/blob/v0.1.0-alpha.7/SECURITY.md). Apache-2.0.
