# Pin: event records (diff.v1)

**What this is.** The shape of diff.v1's event records, written by hand for the author's approval
(decision 2026-10-31, Q5). A path record carries findings about its own path only; a fact about a
package -- installed, removed, upgraded, downgraded, reinstalled -- is an event record, emitted by
the interpreter's end hook once every path has been seen, listing the paths it was derived from.
An event never decides an outcome: every path it lists has its own record, or is unchanged.

**Changing it.** In its own PR, presented as a table, after the author's explicit OK.

| rule | statement |
|---|---|
| E1 placement | Event records come after the last path record and before the trailer. A diff with none has none. |
| E2 shape | `{"event": "<kind>", "interp": "<interpreter>", <the kind's fields, in finding-kinds.md's order>, "text": "<its template>", "provisional": true, "paths": [...]}`. The kind is an `event`-level kind of finding-kinds.md. `provisional` is present, and `true`, exactly when a path the event was derived from has the outcome `unknown` (decision P7): the event may not hold. |
| E3 paths | The paths it was derived from, relative to the scope as in path records, sorted bytewise, each once, at least one (except `and_more`). `paths_b64` instead -- every element base64 -- when any is not valid UTF-8. |
| E4 order | By interpreter, in the order text, pip, dpkg, git; within one, as the interpreter defines it in finding-kinds.md's terms: pip by normalized name, then kind; dpkg by Package, then Architecture, then kind; git by repository, then `HEAD` before every branch, then branch, then kind (decision 126). The same inputs give the same bytes. |
| E5 bound | At most 65,536 event records per interpreter per diff: past that, the 65,536th is `{"event": "and_more", "interp": ..., "n": <that one and the rest>, "text": "and {n} more", "paths": []}`. An interpreter's per-diff state is bounded to match. |
| E6 failure | An interpreter whose end hook fails emits `{"event": "could_not_interpret", "interp": ..., "text": "could not interpret", "paths": [...], "paths_truncated": <n>}` and no other event: `paths` the first 1,024 of the paths it had claimed (bytewise; never a path E11 withholds), `paths_truncated` the number of the rest, present only when not 0 (decision P4). The diff does not fail. |
| E7 trailer | The trailer gains `events`: the number of event records. `belay_diff_end` still counts path records only. |
| E8 forward | A consumer ignores an event kind it does not know, as it ignores an unknown finding kind or field. |
| E9 invalid | An event an interpreter adds that breaks its kind's row -- a kind not its own, not event-level, or the core's; a field missing, extra, or not a string field's value; text over 1,024 bytes -- is replaced, in its place, by `{"event": "invalid_finding", "interp": ..., "text": "invalid finding", "paths": [<its paths>]}`; the interpreter's other events stand (decisions P1, P5). |
| E10 a file not interpreted | A file an interpreter claims and cannot interpret gives one `{"event": "could_not_interpret", "interp": ..., "text": "could not interpret", "paths": [<the files>]}`; the interpreter's other events stand (the class of decision P1). pip: a dist-info that cannot be named, or a RECORD it must read that cannot be parsed -- that RECORD's path record carries `could_not_interpret` too, unless its outcome is `unknown`, and nothing more is read from it; a name with RECORDs added and removed other than one of each -- one event naming them, their path records carrying nothing (the pairing is known only once every path record is written). dpkg: a status that cannot be parsed -- its path record carries `could_not_interpret` too, unless its outcome is `unknown`. |
| E11 not captured | A path whose outcome is `unknown` with `not_captured` as its only reason -- the side that lacks it excluded it, or it lies below an `unreadable` directory or a mount there (diff-v1, "Present on one side only") -- derives no event: that side was not looked at, so nothing was installed or removed there. Its path record stands. Any other `unknown` path still derives provisional events (E2). No interpreter is given it, so no event of the core's names it either: no `could_not_interpret` (E10) nor `content_unavailable` for it, and a failed end hook's event (E6) never lists it. (Decision 2026-11-02: approved, from the review of #33, D1; the core's events spelled out, decision 118.) |
| E12 git events | git's end hook derives repository-level events from the paths of this diff it explained -- loose refs, `packed-refs`, `HEAD`, reflogs -- per repository (a directory named `.git`; `repo` its path in the scope). A branch is a ref `refs/heads/<branch>`, named without `refs/heads/`. Its value on a side: its loose ref there; else its line in `packed-refs` when `packed-refs` is a path of this diff; else, before only, the old id of the first entry its reflog gained in this diff (all zeros: absent). One event per branch whose existence or commit differs: absent before by that evidence and present after, `git_branch_created`; present after with no evidence of before, `git_branch_moved` with no `from`; its loose ref removed and `packed-refs` without it (a path of this diff, or not -- git removes a branch from both), `git_branch_deleted`; a deletion and a creation at the same commit whose new reflog says `Branch: renamed`, one `git_branch_renamed`. A branch on both sides at different commits is decided by the entries its reflog gained in this diff, when they lead from its value before to its value after (each entry's old id the previous one's new, the first's old the value before, the last's new the value after): any `reset`, `commit (amend)`, operation containing `rebase`, message starting `branch: Reset to`, or message containing `forced-update` -- `git_history_rewritten`; else only commits (`commit`, `commit (merge)`, `cherry-pick`, `revert`, `am`) and fast-forwards or merges (a message containing `Fast-forward`; an operation starting with `merge` or `pull`) -- `git_commits_added`; else, or with no such entries, `git_branch_moved`. `HEAD` naming another branch, or detaching or attaching: `git_head_switched`; `HEAD` detached on both sides at different commits is the branch `HEAD`, decided by `logs/HEAD` as above. Remote-tracking refs and tags derive no event (their path findings stand). A path whose outcome is `unknown` adds no finding to its record (P8) but is read like any other where its copy can be read, as dpkg reads a status (a `raced` file's bytes were true when read, and may be no longer): every event derived from it is provisional (E2), so a branch whose ref raced is never silent. What git cannot read reduces what is claimed, never the fact the refs give: a reflog it cannot read is no evidence -- the move still comes from the refs, as `git_branch_moved`, without a how; a ref or `packed-refs` that cannot be read on a side gives no value there -- before, the reflog's evidence may still give one, and without one the event is `git_branch_moved` with no `from` (a branch only in `packed-refs` too); after, the branch derives no event. The record of a path git cannot read whose outcome is not `unknown` carries `content_unavailable`, and one `content_unavailable` event per reason names those paths (provisional when one of them is `unknown`). `paths`: every ref, `packed-refs` and `HEAD` path whose value the event uses, and a reflog only when its entries were used -- giving the value before or evidence of absence before, a rename, or how the branch moved (entries that lead from before to after but say not how are not used). The reflog is written by the watched process (diff-v1, git): the kinds that rest on it say so. (Decisions 126, 132: approved 2026-11-02, events from an `unknown` path provisional rather than dropped; 137: what cannot be read, and `paths`, worded -- refs are proof, the reflog is evidence.) |
