# Pin: the protect spec, version 2

**What this is.** Version 2 of the protect spec: `no_write` also forbids deleting the path. Deleting is a
write to the file's existence. Replaying 2,115 published agent runs found two where a file a task said not
to write was deleted, and a spec of `no_write` alone said nothing. A version 2 spec is a version 1 spec --
`protect-spec.md`, which stays as the record of version 1 -- with exactly the changes below. Everything
not listed here is as `protect-spec.md` says.

`protect-spec.md` says changing a key's meaning is `belay_protect` 2. Version 1 is dropped, not kept beside
it (author, 2026-11-05): one meaning of `no_write` in the code, and no spec that keeps the gap.

**Changing it.** In its own PR, presented as a table, after the author's explicit OK.

| id | rule |
|---|---|
| PV2-1 | `belay_protect` is `2`. A reader refuses any other value, `1` included: nothing is judged (exit 2, as PS-R2), and the message names what to do: `belay_protect is not 2 (version 1 specs are refused: no_write now forbids deleting; say 2)`. |
| PV2-2 | `no_write`: as PS-M1, and also a path matched before whose outcome is `removed`. That is `protected_path_deleted`, not `protected_path_written`. |
| PV2-3 | `no_delete` is unchanged (PS-M2) and stays valid: alone, it forbids deleting and allows writing. With `no_write` it adds nothing. A path gives one `protected_path_deleted`, whichever modes ask for it. |
| PV2-4 | `protected_path_deleted`'s text is `{path}: protected by {rule}, removed`, for both modes. Its `rule` is the pattern of the first rule that matches the path and has `no_write` or `no_delete`. Its fields, level and place in the flags' order are as policy-v1 says; this row replaces that row's text and its source. `belay_policy` stays 1: no key changes. |
| PV2-5 | PS-M5's "a side its modes read": `no_write` reads the before side for deletion too. V4-S2 already covers a one-sided `unknown` path. A path flagged at reset (`unreadable`, `unverified`) and then removed gives both `protected_path_deleted` and `protected_path_unverifiable`, as under `no_delete`. |
| PV2-6 | The bundle format does not change. A bundle holds its spec's digest, not its meaning: a bundle exported with a version 1 spec can only be verified with that spec, which is refused (PV2-1), so it must be exported again. A bundle exported without a spec is unaffected. |
| PV2-7 | PS-M5 is unchanged by the diff's `content_not_read` (diff-fields O9), and already covers it: a path a rule matches whose record is `modified` or `metadata_only` and whose entry, on a side the rule's modes read, is `unverified`, `unstable`, `unreadable` or a `mount` is `protected_path_unverifiable`, as well as whatever its fields prove (policy-v1 P-G2). |
| PV2-8 | `no_delete` reads existence only. This amends how PS-M5 applies to it, and the `no_delete` half of PV2-5's last sentence; PS-M5 stands for every other mode. Under a rule whose only mode is `no_delete`, a matched path present on both sides is not `protected_path_unverifiable`, whatever its entries carry (`unverified`, `unstable`, `unreadable`, `mount`, `raced`, `writer_open`) and whatever its outcome, `unknown` included: it is there. One removed is `protected_path_deleted` and nothing more, whatever its entry carried at reset. It is `protected_path_unverifiable` only when its existence after cannot be established: it is on one side only and its outcome is `unknown` -- as V4-S2 says of every rule -- for the reasons the diff gives such a path: `not_captured` (below a directory that was not listed or a mount, or excluded), `listing_incomplete`, `raced`, `writer_open`. A rule that also has `no_write` or `no_create`, an `expected_sha256`, or another rule matching the path, reads what it reads today. `belay_policy` stays 1 and the spec's version 2. Approved by the author, 2026-11-19: "no_delete reads existence only." Run on the branch before this row: a protected file rewritten longer and left mode 000 under a `no_delete`-only rule gave `protected_path_unverifiable`, exit 1. |
| PV2-9 | `no_delete` reads existence only, and a path under it is `protected_path_unverifiable` only when its existence cannot be established. For a directory that includes what the rules protect below it. Where every rule matching a path has `no_delete` as its only mode, a matched directory nothing was seen below on a side -- its entry there carries `unreadable` or `mount` -- is `protected_path_unverifiable`, with the `reasons` PS-M5 gives, also when it is removed (it is then `protected_path_deleted` too). What lies below it has no entry on that side: it cannot be shown to exist, and a file deleted there leaves no record of its own. This is the one exception to PV2-8's "whatever its entries carry"; PV2-8 stands for every other path: a file that is there is there. Run before this row, as an unprivileged user under a `no_delete`-only `grader/**`: with `grader/sub` mode 000 at reset, then opened and a file below it removed, `verify` exited 0. Confirmed by the author, 2026-11-19. |
| PV2-10 | PV2-8 and PV2-9 hold for a path only when **every** rule that matches it has `no_delete` as its only mode and no `expected_sha256`: "under `no_delete` alone" (the author, 2026-11-19). When any other rule matches the path as well, in either order, the path is judged as before PV2-8: every `no_delete` rule reads the before side again, and PS-M5 applies whatever the outcome. Run before this row: a `no_delete`-only `grader/**` followed by a `no_create` rule on `grader/key`, the key mode 000 at reset and then rewritten readable, exited 0 where the release before PV2-8 gave `protected_path_unverifiable`. |
| PV2-11 | Under such rules alone, a path that was not there at reset and is there after is no finding, whatever its entry carries (`unreadable` included): `no_delete` has nothing to say about a file that was created. Before PV2-8 an added unreadable file was `protected_path_unverifiable` there; that is the one change of answer PV2-8 makes for a path with a record on one side whose outcome is `added`. A one-sided path whose outcome is `unknown` stays unverifiable (PV2-8). Confirmed by the author, 2026-11-19. |
| PV2-12 | PV2-9 also holds for a matched directory whose listing was incomplete on a side: its entry there carries `unstable`. A child missing from that listing has no entry on that side, and one deleted later leaves no record of its own; so under rules that are `no_delete` alone the directory is `protected_path_unverifiable`, with the `reasons` PS-M5 gives (`unstable`), also when it is removed (it is then `protected_path_deleted` too). PV2-11 stands: a directory that was not there at reset is no finding, whatever its entry carries. Run before this row, with manifests written by hand: under a `no_delete`-only `grader/**`, a `grader/sub` carrying `unstable` on both sides gave no record and no violation; so did one carrying it at reset only, or after only. Status: the builder's reading, awaiting the author's OK with the rest. |
